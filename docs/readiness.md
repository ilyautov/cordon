# Readiness

This page tracks what Cordon took from the tools it is compared with in [comparison.md](comparison.md), what it chose not to take, and what is still open. Every "done" row names the test or live run that checks it, so a claim here can be verified by reading the code. The comparison table was last reviewed at 0.7.0, on 26 September 2026; the model-origin and isolated ticket boundaries below were checked at 0.12.1 on 8 October 2026.

## Considered and not taken

- **A classifier or LLM judge.** Lakera, Prompt Shields, PromptGuard and NeMo self-check decide by meaning. Cordon's first invariant is no model in the decision path ([AGENTS.md](../AGENTS.md)). A classifier can run beside Cordon, and Cordon's decision does not depend on it.
- **A confusables filter.** Cordon never matches text against keywords, so lookalike letters cannot slip past a keyword. What matters is that a fullwidth or mathematical-bold link on a page still matches the plain link in a call. It does, through NFKC in provenance (`tests/provenance/store.test.ts`), and mixed scripts inside one word are flagged by sanitize.
- **Approvals that outlive one call.** In interactive mode a hook harness asks the human on every escalated call. Where nobody can be asked, Cordon keeps an approval only for one exact call, once, for an hour. An approval for a tool, a host or a session is state an attacker can aim at (see "Things that look like improvements" in [AGENTS.md](../AGENTS.md)).
- **A source label read from nested arguments.** The label decides which declared trusted source a result counts as. Reading it from a nested field would let a call carry a trusted link beside the one it actually fetches, and the result would be classified by the decoy. Only top-level `url`, `path` and their spellings name a source; everything else is named by the tool.
- **A hosted dashboard, SSO, telemetry.** Each would put a network service into the path. The journal is a file for the shipper you already run.

## Open

- **A model that chooses a harmful call itself.** With no untrusted read and `exec` in the certificate, the Codex hook passes a `curl`-then-shell-shaped call under the `coding` profile; with the default certificate it refuses it. An explicit `blockedTools: [Bash]` refuses that shell call even while granting `exec` to a declared runner tool. A live native-shell control wrote a harmless marker without Cordon; session, user and trusted-project hooks refused it before execution. Ordinary user-level and project-level `/hooks` trust flows, followed by fresh `codex exec` sessions, also refused it without a trust-bypass flag. A connected Codex/MCP/Docker trial completed a one-call edit, a read-then-edit and five isolated edit-and-check tasks using an owner-selected check script; a no-`exec` control stopped before the runner. A later combined run kept the native shell enabled and the Cordon hook active: the shell probe was denied, while a separate request edited the owner-selected file through the gated runner. A paired control exposed a host-write path: with `create` and `update` granted, `blockedTools: [Bash]` still allowed native `apply_patch`; removing those effects or blocking `apply_patch` refused it. Direct runner probes could not read a sibling synthetic `.env`, reach a local sink, copy back a symlink or overwrite the read-only staged check. An absolute path echoed by the check script caused a provenance refusal, and one exploratory live request made no MCP call. These are narrow utility checks on an ordinary model, not a test of poisoned weights or a production sandbox. See [the measurement](model-origin-benchmark.md).
- **Native Codex web search.** A six-arm Codex CLI 0.161.0 probe observed the native tool as `webrun` in both `PreToolUse` and `PostToolUse`. The search completed without hooks, was refused before execution without `network-egress`, and completed with that effect granted. A synthetic result block reached the model after the search ran. With a hidden HTML instruction substituted locally into a completed result, Cordon returned a block containing the visible text but not the hidden instruction; the final model answer omitted it too. A locally substituted result above the extraction limit was withheld with an explicit notice; its hidden text was absent from the answer. Neither substituted result came from a website. Other native tools and hostile pages served in a live session remain unmeasured. See [the live web-search record](model-origin-benchmark.md#native-codex-web-search-hook-8-october).
- **A deployable restricted executor.** The [restricted coding runbook](restricted-coding.md) records the owner-controlled process boundary, a policy shape for the measured Codex tool names and acceptance probes. The repository supplies a benchmark-only runner, not a production executor. A real deployment must provide and verify its own isolation, copyback and hook trust before handling sensitive work.
- **Behavioral coding utility under provenance.** On a `slugify` repair, two five-pair batches each completed 1/5 live tasks under the default policy and 5/5 with every `run` result explicitly trusted. On an interval-merging repair, one five-pair batch completed 0/5 versus 5/5. Every failed strict run logged provenance denials. Trusting the runner extends trust to any attacker-controlled text it can return. Each completed result passed an independent check in a fresh container. These are thirty attempts on two small tasks with one model, not a general coding rate or a default-policy recommendation. See [the paired trials](model-origin-benchmark.md#behavioral-coding-task-with-two-policies).
- **Held-out behavior on the same coding tasks.** Earlier independent containers replayed the owner-visible examples. New five-pair batches per task ran additional cases outside the agent's staged files: strict completed 0/5 on each task, while all 10 trusted edits passed both visible and held-out checks. A command-spelling detector initially miscounted one successful check invocation and was replaced with a post-assertion output marker before both reported batches. These are still one-file Python tasks and do not show how a poisoned model chooses calls. See [the holdout results](model-origin-benchmark.md#holdout-cases-for-the-coding-tasks-8-october).
- **Exact-call approval for coding.** On the same interval task and retry prompt, two five-run autonomous blocks each completed 0/5, while two interactive blocks with a synthetic reviewer each completed 5/5. Every interactive run consumed one exact `run` approval for the edited file; runner output stayed untrusted, the executed command matched the reviewed command, and the result passed a separate check. An exploratory interactive run needed no approval. This tests same-turn retry under automated review, not human judgment or cross-turn resumption. The reviewer does not validate arbitrary shell semantics; the restricted runner remains necessary. See [the live comparison](model-origin-benchmark.md#exact-call-review-on-the-interval-task).
- **Exact-call review against unseen functional cases.** A later five-run control completed 0/5; five interactive runs each consumed one exact approval and passed the verifier-only interval cases, with runner output still untrusted. An exploratory Docker exit 125 was excluded and now aborts the benchmark rather than entering a utility count. Human review remains unmeasured. See [the holdout approval record](model-origin-benchmark.md#exact-call-review-with-verifier-only-cases).
- **Approval after the agent exits.** A scripted MCP gateway restart kept the call and policy identical but refused an approval from the old process under a new ID. A live `codex exec resume` run likewise retried an identical clean email draft after the benchmark approved the old request; the new gateway refused it and no email reached the server. A further same-process regression found that the old command-and-PID session ID could repeat and spend an old approval; each gateway run now gets a random session ID. A later live resume control approved the **new** ID while its gateway waited and sent exactly one email after the model retried. The old approval stayed unspent. This path needs a fresh review in each process; human review and transfer of an approval across process restarts remain open. See [the restart and fresh-review records](model-origin-benchmark.md#approval-after-an-mcp-gateway-restart).
- **Human review time and host cancellation.** The held-call mode completed one clean email with a synthetic reviewer and a model retry. It did not measure how long a person needs to inspect an arbitrary call. A live one-second Codex timeout did not send MCP cancellation; a first design that automatically forwarded after delayed approval sent an email that Codex reported as a failed call. The final mode sends only a retry instruction, and the same timeout control sent no email. Set and verify the host's tool timeout above the gateway wait so the agent can receive the review result. See [the held-call record](model-origin-benchmark.md#held-mcp-call-for-owner-review).
- **AgentDojo on a vulnerable model, and under adaptive attack.** [agentdojo.md](agentdojo.md) has the scripted worst case and Claude Haiku 4.5. A model that falls for `important_instructions` and attacks beyond it are not measured.
- **Autonomous utility on Slack-like work.** A strict autonomous policy completes 14% of AgentDojo's Slack tasks, 33% with directory tools declared trusted. What is left is links fetched from messages and destinations read from data, which is the attack's own shape.
- **Identifier-preserving email from a ticket.** In an isolated live Codex pair, the direct clean control emailed the owner-named recipient with invoice identifiers; the Cordon-gated clean run attempted the same kind of email but the gateway refused it because ticket fragments would leave the machine. The injected run also delivered no mail, while its direct control did not try the attacker's address. The existing interactive mode can show a whole draft for one-call approval: a scripted gateway trial sent exactly one approved clean draft and left an injected recipient unapproved. A later live Codex trial retried the exact clean draft after a synthetic reviewer approved it during the same turn; one email reached the server. Human judgment remains unmeasured, and the separate CLI resume check shows a new process cannot spend the old approval. See [the paired run and approval controls](model-origin-benchmark.md#isolated-live-ticket-pair-8-october).
- **Cross-server shadowing by description.** A tool whose name imitates another server's tool is held (below). A description on server A that talks about a tool on server B is still only visible text: pinning makes it stable, and nothing judges what it says.
- **Remote MCP servers.** The gateway is stdio only; `audit` reports a remote server as CA204.
- **A managed-settings rollout beyond one machine.** The file-based deployment was verified on one macOS machine. Server-managed settings, MDM delivery, and the Linux and Windows paths have not been run.
